# Farming-game agent system: Codex + Claude Code

**Research date: September 18, 2026.** Shared behavioral sources, generated native adapters, and an operational workflow for GitHub-tracked development. This kit does not change Vesper and does not install a running supervisor.

## Recommended design

Maintain **one role definition and one skill source**, with separate generated Codex/Claude wrappers for their native configuration. A universally identical native agent file would discard platform-specific controls; two independently edited families would drift. The generator preserves shared role text while keeping each platform's model, effort, permissions/tool surface, isolation, and supported limits in its own format. Current platform facts and source identifiers are in `.agents/references/SOURCES.md`. [S01–S08]

The main session acts as orchestrator when you ask it to implement an issue. It uses specialists selectively: a reader for unfamiliar code, one or more coders for bounded scopes, a fresh reviewer, and a PR manager. Tests, documentation, architecture, CI investigation, and asset work get their own roles when the task actually needs them. A library of 13 roles does not mean 13 model calls for every issue.

Root `AGENTS.md` is 437 words. `CLAUDE.md` imports it. Roles and primary skills are short; detailed recovery, budgeting, and delivery procedures load on demand. GitHub issues still hold requirements, decisions, acceptance, and progress. The operational references here are reusable contributor instructions, not parallel game feature plans.

## Art production workflow

Visual asset production uses a **hybrid PixelLab MCP workflow**: development agents may generate and organize candidate characters, animations, terrain, and objects through PixelLab MCP; human review decides what is acceptable; and close-but-imperfect candidates are manually refined in **Aseprite** before Unity import and in-game acceptance. Generation is intentionally not treated as autonomous final art production.

## Recommended issue lifecycle

```text
Implement issue #123
        ↓
Top-level orchestrator reads scope and authority
        ↓
Focused reader, only when needed
        ↓
Branch created from the verified base
        ↓
One coder, or isolated independent worker branches
        ↓
First meaningful pushed commit → draft PR
        ↓
Integrate → targeted tests → independent current-head review
        ↓
PR manager reconciles CI/comments
        ├── actionable finding → coordinator → scoped repair
        └── all applicable gates + authorization → merge
                                                     ↓
                                verify merged → selectively clean/retain branch
```

**Branch first; draft PR early, after a real commit.** This makes accepted work identifiable without forcing empty planning commits. One owner integrates the PR branch. Parallel workers do not all mutate/push the same checkout. The complete integrated result needs review; individually correct slices can still interact badly.

**Branch lifetime is explicit.** An issue-ephemeral branch can be deleted only after confirmed merge and no remaining work/consumers. A persistent iteration branch stays, even if its entire lifetime concerns one issue. Unknown lifetime means retain, not guess.

Draft status does not decide CI cost by itself. Configure readiness and queue events and required gates deliberately. Current-head review, checks, acceptance, and authorization must agree; an internal AI report is not a GitHub-required approval/status. See `.agents/references/git-pr-lifecycle.md`. [S16–S20]

## Stalls and escalation

Do not kill an agent because a legitimate build is slow. Inspect meaningful progress, failing hypotheses, active tool state, and remaining scope. Two ineffective repair hypotheses on the same finding trigger a preserved escalation by default. A first red regression test is expected, not failure to code.

Stop the worker, confirm it and its subprocesses can no longer write, preserve the patch/commits and diagnostic record, then transfer the exclusive write lease. The advanced coder receives the failed approaches and exact remaining question, not merely the original request. One bounded advanced intervention is the default automatic cap; optional deep rescue requires approval. Counts persist across replacement agents.

Treat missing tools, credentials, rate limits, and unclear requirements as their own problem classes. Upgrading a model cannot repair a missing permission. Runtime timings/turn caps in the kit are starting guardrails, not empirically calibrated productivity expectations.

## The important implementation boundary

Native files can guide delegation in a live session. They do not create a persistent process that watches GitHub after that session exits. Mixed-vendor dispatch, reliable time/usage enforcement, restart recovery, and guaranteed cancel-and-reassign behavior require a supervisor around supported runtime interfaces. The kit documents the interface/state contract and supplies a ready-to-file engineering task; it does not pretend that supervisor exists. [S21–S22]

Start with one native runtime per run. Verify routing and safe worktree behavior before building cross-provider orchestration. Use events or native waits instead of repeated LLM polling. A small controller should own deterministic state/permissions; models should decide and implement, not continuously ask whether CI is finished.

Read-only prose is not a permission boundary. Inherited connectors and shell access need real restriction. Keep merge/publishing credentials away from untrusted code execution. Unattended merge is intentionally disabled pending capability verification; once approved, a standing repository/risk policy can avoid repeated routine confirmation.
